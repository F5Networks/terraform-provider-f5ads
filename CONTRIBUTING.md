## Development Requirements

To develop and test the provider, you'll need:

- [Go](https://golang.org/doc/install) >= 1.26
- [Terraform](https://www.terraform.io/downloads) >= 1.0
- [Git](https://git-scm.com/)
- An F5 ADS organization with client credentials for testing

## Getting Started

1. **Fork and Clone the Repository**

   ```bash
   git clone https://github.com/F5Networks/terraform-provider-f5ads.git
   cd terraform-provider-f5ads
   ```

2. **Install Dependencies**

   ```bash
   make deps
   ```

3. **Set Up Environment Variables**

   For testing, you'll need to set up your F5 ADS credentials:

   ```bash
   export F5ADS_GEO="us"
   export F5ADS_CLIENT_ID="your-client-id"
   export F5ADS_CLIENT_SECRET="your-client-secret"
   export GOOGLE_PROJECT="your-google-project-id"
   ```

## Building the Provider

To build the provider locally:

```bash
make build
```

### Local Testing

To test the provider locally with Terraform, you can override the provider installation:

1. Build the provider:
   ```bash
   make install
   ```

2. Create or update your `~/.terraformrc` file:
   ```hcl
   provider_installation {
      dev_overrides {
         "registry.terraform.io/F5Networks/f5ads" = "/path/to/your/go/bin"
      }
      # For all other providers, install them directly from their origin provider
      # registries as normal. If you omit this, Terraform will _only_ use
      # the dev_overrides block, and so no other providers will be available.
      direct {}
   }
   ```

3. Set `TF_CLI_CONFIG_FILE` to your `.terraformrc` file.
   ```sh
   export TF_CLI_CONFIG_FILE=~/.terraformrc
   ```

4. Navigate to the examples directory and test:
   ```bash
   cd examples
   cd path/to/use-case
   terraform plan
   terraform apply
   ```

## Testing

### Unit Tests

Run unit tests with:

```bash
make test
```

Or with verbose output:

```bash
go test -v ./...
```

### Acceptance Tests

Acceptance tests create real resources in your F5 ADS organization. Make sure you have valid credentials configured before running these tests.

```bash
make testacc
```

To run specific acceptance tests:

```bash
TF_ACC=1 go test ./internal/provider -v -run=TestAccDeploymentResource
```
> [!WARNING]
> Acceptance tests create real resources that may incur costs. Make sure to review and clean up resources after testing.

### Linting

Ensure code quality with golangci-lint:

```bash
make lint
```

## Documentation

The `docs/` directory is auto-generated by [tfplugindocs](https://github.com/hashicorp/terraform-plugin-docs) and is committed to the repository. The CI `generate` job verifies it stays in sync — PRs that change schemas or descriptions without regenerating will fail CI.

### When to regenerate

Documentation needs to be regenerated when any of the following changes are made:

- Add or remove a resource or data source
- Add, remove, or rename a schema attribute
- Edit the `Description` of any schema attribute or schema block

```bash
make generate
```

Commit the resulting changes to `docs/` alongside your code changes.

### Writing schema descriptions

Every schema attribute and block must have a `Description` field. Descriptions are the sole source of content for the generated attribute tables in the docs, so they should be genuinely useful to a practitioner. Keep the following in mind:

- Write a complete sentence that explains what the attribute does, not just restates its name.
- State valid values or expected format where it is not obvious (e.g. `"tcp"` or `"udp"`, a CIDR prefix, a fully-qualified resource name).
- Note if changing the value forces the resource to be replaced.
- For provider-level attributes, note the fallback environment variable (e.g. `Can also be set with the F5ADS_ENV_VAR_FOO environment variable.`).

### Import examples

If a resource supports `terraform import`, include a shell example at `examples/resources/<resource_name>/import.sh` showing the import command. `tfplugindocs` picks this up automatically and adds an Import section to the generated documentation.

```bash
# examples/resources/f5ads_deployment/import.sh
terraform import f5ads_deployment.example <id>
```

## Contributing Guidelines

### Report a Bug

To report a bug, open an issue on GitHub with the label `bug` using the available bug report issue template (if available). Please ensure the bug has not already been reported by checking the [issue tracker](https://github.com/F5Networks/terraform-provider-f5ads/issues).

**If the bug is a potential security vulnerability, please report it using our [security policy](./SECURITY.md) instead of opening a public issue.**

When reporting a bug, please include:
- A clear, descriptive title
- Steps to reproduce the issue
- Expected vs actual behavior
- Provider version
- Terraform version
- Relevant configuration snippets
- Any error messages or logs

### Suggest a Feature or Enhancement

To suggest a feature or enhancement, please create an issue on GitHub with the label `enhancement` using the available feature request issue template (if available). Please ensure the feature or enhancement has not already been suggested.

### Open a Pull Request

- Fork the repo, create a branch, implement your changes, add any relevant tests, and submit a PR when your changes are **tested** and ready for review.
- Fill in the PR template (if available).
- Provide a clear description of the changes
- Reference any related issues
- Ensure all CI checks pass

> **Note:** If you'd like to implement a new feature, please consider creating a feature request issue first to start a discussion about the feature.

#### F5 Contributor License Agreement (CLA)

F5 requires all contributors to agree to the terms of the F5 CLA (available [here](https://github.com/f5/f5-cla/blob/main/docs/f5_cla.md)) before any of their changes can be incorporated into an F5 Open Source repository.

If you have not yet agreed to the F5 CLA terms and submit a PR to this repository, a bot will prompt you to view and agree to the F5 CLA. You will have to agree to the F5 CLA terms through a comment in the PR before any of your changes can be merged. Your agreement signature will be safely stored by F5 and no longer be required in future PRs.

#### Pull Request Guidelines

- Keep changes focused and atomic
- Include tests for bug fixes and new features
- Update documentation for user-facing changes
- Follow the existing code style and conventions
- Write clear commit messages following the guidelines below
- Keep a clean, concise and meaningful git commit history on your branch (within reason), rebasing locally and squashing before submitting a PR

## Code Guidelines

### Go Code Style

- Follow standard Go formatting guidelines (`gofmt`)
- Use meaningful variable and function names
- Add comments for complex logic
- Keep functions focused and single-purpose
- Follow the [Terraform Plugin Framework](https://developer.hashicorp.com/terraform/plugin/framework) best practices

### Git Commit Guidelines

- Keep a clean, concise and meaningful git commit history on your branch (within reason), rebasing locally and squashing before submitting a PR.
- If possible and/or relevant, use the [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/) format when writing a commit message, so that changelogs can be automatically generated.
- Follow the guidelines of writing a good commit message as described here <https://chris.beams.io/posts/git-commit/> and summarized in the next few points:
  - In the subject line, use the present tense ("Add feature" not "Added feature").
  - In the subject line, use the imperative mood ("Move cursor to..." not "Moves cursor to...").
  - Limit the subject line to 72 characters or less.
  - Reference issues and pull requests liberally after the subject line.
  - Add more detailed description in the body of the git message (`git commit -a` to give you more space and time in your text editor to write a good message instead of `git commit -am`).
